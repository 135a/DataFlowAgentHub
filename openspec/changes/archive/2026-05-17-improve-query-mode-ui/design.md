## Context

当前前端消息输入区域使用一个 checkbox 控制"深度分析"模式，用户无法直观了解两种模式（快速查询 / 深度分析）的区别。处理过程中仅显示文本状态，缺乏进度反馈和时间预估，用户体验差。

所有改动均为纯前端，后端无需修改。

## Goals / Non-Goals

**Goals:**
- 将 checkbox 替换为两个显式模式选择按钮，选中状态有颜色区分
- 输入框下方展示当前模式的描述说明，帮助用户理解差异
- 两种模式在处理过程中均展示步骤进度面板，包含状态图标和进度条
- 实时显示已用时间和预估剩余时间
- 默认模式可持久化（localStorage）
- 时间预估首次使用硬编码默认值，后续使用历史实际耗时的平均值

**Non-Goals:**
- 不涉及后端代码改动
- 不改变现有 API 请求/响应格式
- 不改变 LangGraph 工作流逻辑
- 不添加新的第三方依赖

## Decisions

### D1: 模式选择器使用双按钮而非下拉框或单选组

**选择**：两个并排的 pill 样式按钮，选中态填充颜色，未选中态镂空边框。

**理由**：两种模式是并列关系，按钮视觉权重高，用户一目了然。比下拉框更直接，比 radio group 更现代。

### D2: 快速查询使用蓝色，深度分析使用紫色

| 状态 | 快速查询 (#2563EB) | 深度分析 (#7C3AED) |
|------|-------------------|-------------------|
| 选中 | 蓝底白字 | 紫底白字 |
| 未选中 | 蓝框蓝字 透明底 | 紫框紫字 透明底 |
| Hover | 淡蓝底 `#EFF6FF` | 淡紫底 `#F5F3FF` |

**理由**：蓝色传达快速/可靠，紫色传达深度/分析，视觉上容易区分。

### D3: 进度面板使用现有 SSE 事件驱动，零后端改动

快速查询的两个步骤（SQL 生成、执行查询）由 `sql_generated` 和 `result` SSE 事件驱动。

深度分析的四步骤由 `agent_step` SSE 事件的 `agent_name` 字段驱动（nl2sql_node → analysis_node → chart_node → report_node）。

**理由**：后端已经在发这些事件，无需修改任何后端代码。

### D4: 时间预估使用历史平均值

首次没有历史数据时使用硬编码默认值：

| 模式 | 步骤 | 硬编码默认值 |
|------|------|-------------|
| 快速查询 | SQL 生成 | 1-3s |
| 快速查询 | 执行查询 | 0.1-0.5s |
| 深度分析 | SQL 生成 | 1-3s |
| 深度分析 | 数据分析 | 2-5s |
| 深度分析 | 图表绘制 | 3-6s |
| 深度分析 | 报告生成 | 1-3s |

每次查询完成后，将各步骤实际耗时存入 localStorage。后续查询以历史实际耗时的平均值作为初始预估。

### D5: 模式描述框位于输入框下方

模式切换时显示简短说明，告知用户当前模式的能力范围和预估时间。选择快速查询时切换为快速查询描述，深度分析时为深度分析描述。

## Risks / Trade-offs

- **时间预估在首次使用时可能不准** → 硬编码默认值为较宽的保守估计（如"5-15 秒"），随着使用次数增加自动收敛
- **SSE 事件可能丢失** → 同步路径快速查询下 SseEvent 可能极快到几乎瞬间完成，前端需要在 HTTP 响应中已有 sql 和 rows 的情况下优雅兜底
- **localStorage 被清除** → 回退到硬编码默认值，每次查询完成后重新写入
